Dynamic Workflows を極める
― 6 パターン・14 ステップ

Anthropic のエンジニアが実際に使う「Claude が自分でハーネスを書く」やり方。50 個のプロンプトを、たった 1 本のワークフローに畳む。

原典：@0xCodez（X／2026-06-03 投稿、@0xMovez 経由で拡散）／ 日本語訳・再構成

14 ステップ。6 パターン。50 個のプロンプトの代わりに、ワークフロー 1 本。

Claude Code ユーザーの大半は、いまだにワークフローを手作業で書いている。プロンプトを数珠つなぎにし、出力をコピーして次のプロンプトに貼り、おかしくなったところを直し、それを繰り返す。ビルダーの 10 人に 9 人は、2 週間前にリリースされた Dynamic Workflows をまだ一度も試していない。

Dynamic Workflows は 2026 年 5 月 28 日に Claude Code にリリースされた。デフォルトのハーネスはコーディング向けで、ほとんどのタスクではそれで十分だ。だが 1 つのコンテキストウィンドウでは破綻し始める種類の作業がある ―― 長時間に渡る・大規模に並列・高度に構造化・敵対的(adversarial)な作業だ。こうした作業のために Anthropic はこれまで自前でカスタムハーネス(Research、Code Review、エージェントチーム)を組んでいた。Dynamic Workflows では、Claude がそのハーネスを、あなたのタスク向けにオーダーメイドで、その場で JavaScript で書いてくれる。

Part 1 · メンタルモデル

01ワークフローとは、Claude が書くハーネスである

デフォルトのハーネスでは、Claude が計画と実行を同じコンテキストウィンドウで行う。ほとんどのコーディング作業ではこれで快適だが、長時間・並列・敵対的な作業では破綻する。Dynamic Workflow とは、Claude がそのタスク用に自前のカスタムハーネスを書くこと ―― サブエージェントを生成・調整する数個の特別な関数と、その間を流れるデータを処理する標準 JavaScript(Math・JSON・Array)からなる JS ファイルだ。

@_catwu（5/29）：私たちの最も強力な新機能、dynamic workflows を共有できて嬉しい。プロンプトで "workflow" と言及すれば、Claude が動的にオーケストレーション計画を作り、それを厳密に守る。すべての段階が正しい順序で実行されると安心して信頼できる。

デフォルトのハーネスにはできない、3 つのことが手に入る：

エージェントごとの隔離
各サブエージェントが、1 つに絞られたゴールを持つ専用コンテキストを得る。相互汚染なし。
エージェントごとのモデル選択
難しい推論には Opus、安価な探索には Haiku、中間には Sonnet ―― 各エージェントに最適なモデルを割り当てる。
エージェントごとの隔離レベル
Worktree(隔離 git チェックアウト)か remote(チェックアウトなし)か。各エージェントに必要なものを選ぶ。

開始方法は 2 つ。Claude に直接頼む（「○○するワークフローを作って」）か、トリガーワード ultracode を使う。ワークフローが中断されても(ユーザー操作・ターミナル終了)、セッション再開で中断点から続行できる。

02ワークフローが解決する 3 つの失敗モード

Claude が複雑なタスクに単一コンテキストで長く取り組むほど、Anthropic のローンチ文書で名指しされた 3 つの失敗モードに陥りやすくなる。ワークフローはこの 3 つすべてを構造的に解決する。自分のタスクがこれらに苦しんでいるなら、それがワークフローに手を伸ばすサインだ。

① エージェント的怠惰（Agentic laziness）
複雑な多段タスクを終える前に止まり、部分的な進捗だけで「完了」と宣言する。セキュリティレビュー 50 項目中 20 項目だけ対応して、残りを「処理済み」と言ってしまう。
② 自己選好バイアス（Self-preferential bias）
検証・判定を求められると、Claude は自分自身の結果を好む。利害関係を持つ検証者は、公正な検証者になれない。
③ ゴールドリフト（Goal drift）
多数ターンにまたがり当初目的への忠実度が徐々に失われる。特にコンパクション後。「X はするな」という制約が、47 ターン目で静かに消える。

03静的ワークフロー vs 動的ワークフロー

Claude Agent SDK や claude -p で静的ワークフローを組んだことがあるかもしれない。静的ワークフローは汎用的で、あらゆるエッジケースに備えて一度だけ書かれる ―― 機能はするが保守的にならざるを得ない。

Dynamic Workflows は違う。Claude がこのタスクのためにこのワークフローを書く。動的版が勝つ理由は検索ステップではなく、ワークフローがあなたの文脈に合わせて自らの形を整えられる点にある ―― あなたの課金コードを読み、各機能を実際の新プロバイダ docs と照合し、あなたの取引量で価格を試算し、自ら導きつつある答えに「なぜ移行すべきでないか」という敵対的パスを当てる。静的ハーネスにはこれができない。あなたのコードが存在することすら知らないからだ。

04コア API ― agent() / parallel() / pipeline()

ワークフローの仕事の大半は、この 3 つの関数がこなす。これを知っていれば、Claude が書くどんなワークフローも読めるし、特定の形にしたいとき後押しできる。

  • agent() ― サブエージェントを 1 体生成する。
  • parallel() ― バリア。ファンアウトし、すべてが返るまで待ってから返す。
  • pipeline() ― ストリーミング。各アイテムが各ステージを独立に流れていく。
選び方 問いはひとつ ―「次に何かをする前に、すべての結果が必要か?」 YES なら parallel。NO なら pipeline（全体として安価で速い）。

Part 2 · 6 つのパターン

05Classify-and-act ― 作業の前に作業をルーティングする

分類エージェントがタスクの種類を判断し、その答えに基づいて別々のエージェントや挙動へルーティングする。あるいは最後に分類器を走らせ、生の出力を次工程のためにバケツへ仕分ける。効くのは：タスクが異種混在でサブタイプごとに別扱いが要るとき／高価なモデルを複雑さが要求する箇所だけに使いたいとき(安価に分類→必要時のみ Opus)／作業の分解自体が非自明なとき。

例「auth モジュールの仕組みを説明して」→ 分類サブエージェントがまずコードを読んで複雑さを見積もり、10 ファイルなら Sonnet、100 ファイルなら Opus へ。作業を理解した後で、仕事に合うモデルを決める。

06Fan-out-and-synthesize ― 多数の小ステップ、1 つの統合結果

タスクを多数の小ステップに分け、各ステップにエージェントを並列で走らせ、結果を 1 つの答えに統合する。統合ステップはバリア ―― 全ファンアウトを待ってから構造化出力をマージする。各サブエージェントは自分の担当しか見ないので、オーケストレータが 50 個の無関係な詳細に気を取られず、相互汚染も起きない。

列挙できる作業リスト(50 ファイル/200 endpoint)各項目が独立最後に 1 つの統合答えが欲しい
// ファンアウト：1 ファイルにつき 1 エージェント。バリア：全部を待つ。
const reviews = await parallel(
  files.map(file => () => agent(
    `Review ${file} for security issues`,
    { model: "haiku", schema: IssueList }
  ))
)

// 統合：Opus エージェント 1 体がすべてをマージ。
const report = await agent(
  `Merge these reviews into one prioritized report:\n${JSON.stringify(reviews)}`,
  { model: "opus" }
)

07Adversarial verification ― 敵対的検証

これは自己選好バイアスへの構造的な解決策だ。生成した各エージェントに対し、その出力をルーブリックに照らして敵対的に検証する別エージェントを走らせる。検証者は元の作業を一度も見ていないので、贔屓できない。

  • 主張チェック：レポートの各事実記述が、専用の検証サブエージェントで元ソースと照合される。
  • コードレビュー：作者エージェントが修正を書き、別コンテキストのレビュアーが見る。同じ Claude が自分を判定することはない。
  • 品質ゲート：出荷前に敵対者が最も弱い点を突く。突けなければ出荷。
ペアリングの鉄則検証者はルーブリックと成果物だけを知るべきで、誰が作ったかは知ってはならない。さもないとプロンプト内のヒント経由で自己選好が忍び込む。

08Generate-and-filter ― 生成してから選抜する

あるテーマで多数のアイデアを生成し、ルーブリックや検証でフィルタ、重複を除去し、最高品質で検証済みのものだけを返す。ブレスト(30 個の名前→検証者が陳腐・商標衝突・語感の弱いものを排除→3 個だけ見せる)、仮説生成、ソリューション設計に効く。

「最良の答えを 1 つ」と頼むと Claude は早期にコミットする。Generate-and-filter は、全選択肢が吟味された後で遅れてコミットさせる ―― これがその正反対。

09Tournament ― ペアワイズ比較は絶対採点に勝る

作業を分割するのでなく、エージェントたちに競わせる。N 体が異なるアプローチで同じタスクに挑み、結果を 1 つが勝つまで 2 つずつ(ペアワイズ)判定する。比較判断は絶対採点より信頼できる ―― 特にセンス依存の作業で。1,000 項目を 1 プロンプトでソートすると品質が劣化し、コンテキストにも収まらない。トーナメントはブラケットを新鮮なエージェントに分散させ、各々がたった 2 項目を比較する。ブラケット自体は決定論的なループコードに存在し、コンテキストには残らない。デザイン・候補選定・コンテンツ優先順位付けにも同じ発想が効く。

10Loop until done ― 終わるまでループ

作業量が不明なタスクでは、停止条件が満たされるまでエージェント生成をループする(新たな発見がない／ログにエラーがない／理論が検証された)。固定回数のパスではなく。

フレーキーテスト：理論が成り立つまでバグハント：1 周ゼロになるまでパターンマイニング：新クラスタが出なくなるまで

/goal(「1 つの理論が機能するまで止まるな」のような厳格な完了要件)と、ワークフロー全体を定期実行したいなら /loop と組み合わせる。ブラケットと停止条件はコードに存在し、コンテキストに残るのはアクティブな反復だけ。

Part 3 · 運用

11パターンを組み合わせる ― 1 つのワークフロー、複数のパターン

6 パターンが単独で現れることはまれで、実際のワークフローは 2〜4 個を組み合わせる。Anthropic のローンチ文書のユースケースとパターンの対応：

ユースケース組み合わせるパターン
マイグレーション／リファクタFan-out(worktree で callsite/失敗テストごと)→ 敵対的検証 → loop until done。Anthropic が Bun を Zig→Rust に書き換えた手法。
ディープリサーチ（/deep-research）Fan-out(並列ウェブ検索)→ 敵対的検証(各主張を独立検証)→ synthesize(引用付き 1 レポート)
ドラフトの深い検証全事実主張を特定 → Fan-out(主張ごとに検証者)→ メタ検証者(ソースの質を確認)
1,000 件以上の仕分けTournament ―― ペアワイズ比較。絶対採点は決してしない。
メモリとルール遵守ルールごとの検証者(fan-out)→ 懐疑者ペルソナがルール自体を見て偽陽性を防ぐ
根本原因の調査バラバラな証拠から理論生成(別々にログ/ファイル/データを読む)→ 各理論に検証者と反証者のパネル → 1 つが生き残るまでループ
大規模トリアージClassify-and-act → 既存チケットと重複除去 → 修正試行 or エスカレーション。/loop で継続化。
探索とセンス（デザイン/命名/UI）Generate-and-filter(5〜20 案)→ ルーブリック付きトーナメント → ランク/選択
軽量な評価(evals)候補を worktree で実行 → 比較エージェントがルーブリック採点 → 改良して再採点

ドリフト → fan-out ／ 自己選好 → 敵対的検証
オープンエンド → loop until done ／ 採点困難 → トーナメント

12/goal・/loop・トークン予算と組み合わせる

ワークフローは高くつくことがある。3 つのコントロールが「クールだが高い」を「無人で回せるツール」に変える。

  • /goal ― 厳格な完了要件を設定。loop と組む。なしだとソフトな完了点で止まるが、ありなら実際の終了条件まで反復する。
  • /loop ― ワークフロー全体を定期スケジュールで実行。トリアージ・週次リサーチ・定期検証など継続運用に。
  • 明示的なトークン予算 ― 「10k トークンを使え」とプロンプトで上限を切る。なしだと野心的なワークフローは予想の 5〜10 倍に膨らむ。
> ultracode quick adversarial review of this assumption:
  "moving to Postgres eliminates our shard rebalancing."
  Use 5k tokens. /goal don't stop until you have either
  a counterexample or three independent confirmations.
Claude Code チームより「ベストプラクティスはまだ発展途上です。Dynamic workflows はしばしばより多くのトークンを使うので、いつ・どう使うかを慎重に考えてください。」 ―― 通常の Claude Code セッションで 5 分で終わるなら、ワークフローは要らない。

13quarantine（隔離）パターン ― 信頼できない入力に

信頼できない公開コンテンツ(サポートチケット・バグ報告・ユーザーフィードバック・スクレイプデータ)を読むワークフローは、その中にプロンプトインジェクションが含まれうると想定すべきだ。対策は quarantine(隔離) ―― 信頼できないコンテンツを読むエージェントには高権限のアクションを一切禁じ、生コンテンツに触れない別エージェントが実際の操作を行う。

入力をあなた自身か信頼できる同僚が書いたのでないなら、隔離せよ。30 行の読み取り専用リーダーエージェントはほぼコストゼロで、プロンプトインジェクションのリスクを丸ごと 1 クラス除去する。

14ワークフローを保存し、Skill として出荷する

機能したら、ワークフローメニューで s を押して保存する。保存先は ~/.claude/workflows。そこから 2 つの道：

  • ローカルに保持 ― 自分のプロジェクト間で再利用する。
  • Skill として出荷 ― JS ファイルを Skill フォルダに同梱し SKILL.md から参照。インストールした誰もが同じワークフローを実行できる。
実務のコツSkill にパッケージするときは、ワークフローを「逐語的に実行するスクリプト」ではなく「テンプレート」として扱うよう Claude に促す。全体構造を保ちつつ、手元の具体タスクに形を適応させる余地が残る。「deep verification」や「triage」のように柔軟さが要るワークフローで特に有用。

トークンを浪費する間違い集

通常セッションで済むのにワークフローを使う
大半のコーディングは 5 人レビュアーのパネルなど要らない。
トークン予算がない
明示上限なしだと予想の 5〜10 倍に膨らむ。
1 エージェントが作業と検証を兼ねる
自己選好で検証者が作業者を贔屓する。両者は分離せよ。
parallel と pipeline を交換可能と思う
バリアが重要 ―― parallel は全部待ち、pipeline はストリームする。
loop で /goal を省く
最初のソフトな完了点で早々に止まる。/goal が厳格な完了を強制する。
信頼できないコンテンツをアクターに届かせる
ユーザー投稿物を処理するなら隔離は任意ではない。
絶対スコアで仕分けする
比較判断のほうが信頼できる。トーナメントを使え。
機能したワークフローを保存しない
毎週同じ形を再プロンプトする羽目に。s で保存し Skill 化せよ。
